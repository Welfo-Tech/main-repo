## Key decisions made this session

**Attachment table design (user-raised question)**
Added `category AttachmentCategory` enum to the Attachment model. Without this, the app cannot distinguish an intake photo from a signed quote from a delivery receipt even if both are attached to the same entity. The three-field combination that gives full context: `entityType` (which table), `entityId` (which row), `category` (what role it plays). `mimeType` handles rendering format separately.

**Number generation via service layer, not DB defaults**
Did not use `@default(dbgenerated("generate_case_number()"))` in schema.prisma. Instead, the sequences and functions are created in the migration but called from the service layer with raw SQL (`SELECT generate_case_number()`). This avoids editing migration files to front-load function creation before CREATE TABLE, keeps schema.prisma clean, and makes the generation logic explicit in the service layer.

**`outstanding_amount` not stored**
Invoice does not have an `outstanding_amount` column. Computed as `totalAmount - paidAmount` in the service layer. PostgreSQL generated columns were considered but Prisma's migration generator does not support them — manual migration edits would be fragile.

**`ticketId` is UNIQUE on service_cases**
A ticket converts to exactly one service case. The FK was correct but Prisma requires `@unique` on the defining side for a one-to-one relation. Added `@unique` to `ticketId` on `service_cases`.

**Technician name removed**
`Technician` no longer has a `name` field. Name comes from `technician.user.name`. Avoids duplication.

**Custom SQL in migration file (not separate)**
Sequences, functions, and trigger are appended to the Prisma-generated migration file rather than stored in a separate `sql/` script. This means `prisma migrate reset` re-creates everything in one step without any additional scripts to remember.

**State transition trigger (V1 scope)**
The `trg_case_status_transition` trigger enforces two rules only: CLOSED is terminal, CANCELLED requires a reason. Full state machine enforcement (e.g. preventing DELIVERED before DISPATCHED) is left to the service layer for V1. DB trigger covers the most dangerous cases only.
